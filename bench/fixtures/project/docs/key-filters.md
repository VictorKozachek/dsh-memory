# Секреты и фильтры индексатора

Индексатор не читает файлы с опасными именами: `*.env`, `*secret*`,
`*credential*`, `.git-credentials`. Такие пути попадают в отчёт `secrets` и не
попадают в память вовсе. Это дешёвая защита до чтения содержимого.

В тексте ключи ищутся по форме, а не по подстроке. PEM-заголовок приватного
ключа (`-----BEGIN … PRIVATE KEY-----`) опознаётся только в начале строки:
настоящий ключ так и выглядит, а описание паттерна в документации — нет.
GitHub PAT — `ghp_` + 36 символов, OpenAI-подобный ключ — `sk-` + 48,
AWS access key id — `AKIA` + 16 заглавных. Голые упоминания маркеров без
формы ключа секретом не считаются.

Ключ в inline-code, списке или fenced-блоке всё равно ловится: маскировать код
нельзя, иначе настоящий ключ уйдёт в индекс и в сниппеты. Ложные срабатывания
на документации проекта — риск: если README описывает формат ключа, он не
должен выпадать из памяти. Поэтому PEM якорится к началу строки, а `sk-`
требует границы слева и справа.

Отсеянный файл не индексируется и не выдаётся поиском. Если файл стал секретом
после предыдущей индексации, его источник удаляется, а старые чанки становятся
`stale`: текст остаётся в базе для аудита, но поиском не выдаётся. Политика
очистки такого текста в MVP не определена.

## Ложные срабатывания

Документация проекта часто описывает форматы ключей и потому похожа на секрет.
Фильтр должен отличать пример из README от настоящего ключа: иначе агент
теряет документацию ровно там, где она нужна. Поэтому проверка идёт по форме
и длине, а PEM — по позиции в строке.

Отчёт индексатора перечисляет отсеянные пути, чтобы человек мог проверить
ложные срабатывания. Если файл отсеян ошибочно, его можно переименовать или
вынести секрет в отдельный файл, который не индексируется.

Настоящий ключ в коде — инцидент, а не задача индексатора: плагин не чистит
git-историю и не отзывает ключи. Он лишь не даёт ключу попасть в память и
сниппеты.
