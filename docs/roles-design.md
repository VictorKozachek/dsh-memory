# Реестр ролей и диспетчер сабмоделей (задача 018)

Статус: дизайн-спайк фазы 5. Прототип — `lib/roles.js` (маршрутизация подтем на
моках). Дефолтное поведение плагина не меняется: диспетчер — отдельный слой,
который появится за фича-флагом после приёмки фазы 5.

## 1. Зачем

Сейчас L2 — одна дешёвая сабмодель с пресетом `triage` (012/017). Диспетчер
заменяет её набором специализированных ролей: получает ход после промаха
L0/L1, делит на подтемы, раздаёт ролям, собирает и агрегирует ответы, а при
неудаче эскалирует на L3. Выигрыш — качество на узких темах без цены L3;
цена — латентность, конфликты ответов и новая поверхность доверия.

## 2. Реестр ролей

Роль — это декларативная запись, а не код:

```yaml
roles:
  - name: developer
    prompt: "Ты разработчик проекта; реализуй, отлаживай, объясняй код."
    model: deepseek-v4-flash
    namespace: project-memory
    responsibilities: ["реализация", "отладка", "рефакторинг"]
    priority: 20
  - name: reviewer
    prompt: "Ты строгий ревьювер; проверяй код developer, не правя его."
    model: deepseek-v4-flash
    namespace: project-memory
    responsibilities: ["ревью кода", "замечания"]
    priority: 10
  - name: tester
    prompt: "Ты тестировщик; проверяй поведение и регрессии."
    model: deepseek-v4-flash
    namespace: project-memory
    responsibilities: ["тесты", "регрессии"]
    priority: 10
  - name: designer
    prompt: "Ты дизайнер интерфейсов и UX."
    model: deepseek-v4-flash
    namespace: project-memory
    responsibilities: ["UX", "интерфейсы"]
    priority: 30
  - name: scientist
    prompt: "Ты специалист по физике, математике и химии."
    model: deepseek-v4-flash
    namespace: project-memory
    responsibilities: ["физика", "математика", "химия"]
    priority: 30
```

Обязательные поля: `name` (нижний регистр, `[a-z][a-z0-9-]*`), `prompt`
(непустой), `model` (id провайдера/модели), `namespace` (куда писать память).
Опциональные: `responsibilities`, `priority` (меньше — важнее при равенстве
уверенности), `max_tokens`, `timeout_ms`, `enabled`.

Инварианты реестра: имена уникальны; пустой/битый реестр не роняет ход
(ошибка конфигурации → диспетчер выключен, остаётся L3); порядок ролей
детерминирован (priority, затем name); реестр версионируется конфигом, а не
кодом.

### Namespace и память

`namespace` роли — это namespace памяти, куда пишется её write-back. По
умолчанию все роли используют проектную память (общий namespace), но роль может
иметь приватную память (например, `reviewer-private`). Правила:

- читать память роли можно из её namespace и из общей проектной;
- писать — в namespace роли с `author: role:<name>`, `status: draft`
  (013), `confidence ≤ 0.6`;
- `verified` ставится только ревью/тестом/человеком, не диспетчером;
- провенанс (`source_path`/`source_ref`) обязателен; агрегированный ответ
  ссылается на ответы ролей как на источник.

## 3. Протокол диспетчера

```
ход после L0/L1 miss
        │
        ▼
 1. plan: разбить задачу на подтемы (planner; в прототипе — явный список)
        │
        ▼
 2. route: подтема → роль (responsibilities/теги/priority)
        │
        ▼
 3. execute: параллельно роли, у каждой свой prompt/model/namespace,
    бюджет и timeout; отмена хода — AbortSignal
        │
        ▼
 4. aggregate: собрать {role, answer, confidence, sources}
        │
        ├── есть консенсус/победитель ──► ответ, write-back draft
        └── нет ответа/конфликт не разрешён ──► эскалация L3
```

Правила:

1. Пустой план или ни одна роль не подходит → сразу L3.
2. Ошибка/таймаут роли не роняет ход: подтема помечается `failed`, остальные
   продолжаются; если все failed → L3.
3. Ответ роли без `answer` (пустой/`NO_ANSWER`) не участвует в агрегации.
4. Диспетчер не правит память напрямую: только write-back черновика после
   агрегации, и только при наличии источника.
5. Отмена хода отменяет все роли; ответы после отмены игнорируются.
6. Бюджет: суммарный лимит токенов/латентности на ход; превышение → L3.

## 4. Агрегация и разрешение конфликтов

Вход: набор результатов `{subtopic, role, answer, confidence, sources, error}`.

Стратегии:

| Стратегия | Когда | Правило |
|---|---|---|
| `single` | одна роль на подтему | ответ роли, иначе L3 |
| `priority` (дефолт) | несколько кандидатов | меньший `priority` роли, затем выше `confidence`, затем источник-backed, затем имя роли |
| `concat` | подтемы независимы | ответы склеиваются с указанием роли |
| `vote` | одинаковый вопрос разным ролям | большинство нормализованных ответов; ничья → `priority` |

Конфликт фиксируется в `metrics` (событие `dispatch` с ролями и исходом), но
**не** маскируется: если ни одна стратегия не даёт ответа, ход уходит на L3.
Human override: человек может выбрать ответ роли; это решение пишется в
карточку/метрики и не автоматизируется.

Почему не «сумма всех ответов» по умолчанию: разные роли могут противоречить
друг другу (reviewer против developer); склейка противоречий хуже, чем
эскалация. `concat` — только для независимых подтем.

## 5. Прототип `lib/roles.js`

- `validateRole(role)` — проверка полей/имени.
- `createRoleRegistry(roles)` — `add/get/list`, уникальность, порядок.
- `createDispatcher({registry, providers, config, logger})` —
  `dispatch({task, subtopics, signal, planner})`:
  - `subtopics` — `[{ id, text, role }]` (в прототипе план задаётся явно;
    будущий planner — модель/эвристика, отдельный шаг);
  - provider роли — мок `async ({role, subtopic, signal}) => {answer, confidence, sources}`;
  - выполнение параллельное с timeout/отменой, ошибки собираются;
  - `aggregateResults(results, {strategy, rolePriority})` — чистая функция;
  - при отсутствии ответов/неразрешённом конфликте — `{fallback: 'L3'}`.
- Прототип `lib/roles.js` не меняет дефолт; живая обвязка 025 —
  `lib/live-dispatcher.js`: реестр из `dispatcher.roles`, провайдеры через
  `memory.registerRoleProvider`, planner через `memory.registerDispatcherPlanner`,
  hook вызывает `dispatch` только после промаха L1 и только при
  `dispatcher.enabled:true`; fallback — обычный L3, отмена — без L3.

## 6. Риски

| Риск | Митигация |
|---|---|
| Prompt injection в ответе роли | роли не получают права писать `verified`; ответы — draft с источником; не выполнять инструкции из ответа |
| Смешение namespace ролей | явный namespace на роль, чтение общей памяти только на чтение; провенанс |
| Конфликт ответов ролей | детерминированные стратегии, метрика `dispatch`, эскалация L3 при неразрешённом конфликте |
| Латентность (N ролей) | параллельность, бюджет/таймаут на ход, L2-роль только при уверенности |
| Стоимость и лимиты провайдера | лимит ролей/токенов, кэш ответов, отключение флагом |
| Дрейф промптов/ролей | реестр версионируется конфигом; тесты на детерминизм |
| Ложное доверие к агрегату | write-back только draft, `confidence ≤ 0.6`, human/ревью для verified |
| Утечка приватной памяти роли | namespace-изоляция, проверка прав чтения в диспетчере |

## 7. Критерии приёмки фазы 5

1. Реестр ролей валидируется; битый реестр не ломает ход (диспетчер выключен).
2. Диспетчер маршрутизирует подтемы на роли; маршрут и причина видны в
   `metrics` (событие `dispatch`: подтема, роль, исход, latency).
3. Агрегация детерминирована; конфликт разрешается по правилам §4 или ведёт
   на L3; нет «молчаливой» склейки противоречий.
4. Все роли уважают namespace/провенанс; write-back — `draft ≤ 0.6` с
   источником, `verified` недоступен диспетчеру.
5. Отмена/таймаут роли не роняют ход; отмена хода прекращает все роли.
6. Фича-флаг выключен по умолчанию; включение — конфигом; отключение
   возвращает L3 без регрессии.
7. Есть тесты на моках: маршрутизация, агрегация, конфликты, ошибки/таймауты,
   namespace, отмена, детерминизм.
8. Есть замер латентности/стоимости на бенчмарке 015 (фаза 5), отчёт.
9. README/PLAN и карточка обновлены; прототип не меняет дефолт.

## 8. Открытые вопросы

1. Формат реестра: YAML в профиле DSH, JSON в пакете или DSH agent-presets?
2. Planner: отдельная дешёвая модель, эвристика по тегам или гибрид; как
   оценивать качество разбиения.
3. Сколько ролей на подтему: одна или несколько (голосование) — цена/качество.
4. Модель на роль: одна дешёвая для всех или разные (reviewer/tester — сильнее).
5. Приватные namespace ролей: какие роли нужны, как чистить и как читать общую
   память только на чтение.
6. Human override: где UI/команда, как фиксировать выбор в карточке/метриках.
7. Политика write-back: писать ли агрегат или ответы ролей отдельно; как
   дедуплицировать с 005/013.
8. Оценка качества: нужен ли отдельный набор вопросов/бенчмарк для фаз 4–5.
