# Протокол работы агентов в dsh-memory

Этот файл читает каждый агент в репозитории и в его git-worktree. Коротко:
**одна задача = один worktree = одна сессия роли = один набор файлов**, а
состояние задач живёт в `.kanban/tasks/*.md`.

План проекта — [`PLAN.md`](PLAN.md), спека нарезки — `.kanban/specs/001-mvp.md`.

## Роли

Роль задаётся пресетом сессии: `dispatcher` (оркестратор), `worker`
(исполнитель), `reviewer` (ревьювер), `verifier` (тестировщик).

| Роль | Где работает | Что делает | Чего не делает |
|---|---|---|---|
| оркестратор | основной чекаут | режет спеку на карточки, закрепляет их за сессиями по порядку id, держит лимит в работе, вливает `ready`-ветки, правит общие файлы | не пишет код задач, не пушит |
| исполнитель | worktree задачи | ведёт одну задачу `todo` → `in-review` | не трогает чужие/общие файлы, не мержит, не тестирует свою работу |
| ревьювер | worktree задачи, только чтение | читает диф: принял → `testing`, замечания → `in-progress` | не правит код задачи |
| тестировщик | worktree задачи, только чтение | проверяет независимо: прошло → `ready`, нет → `in-progress` | не правит код задачи |

## Раскладка сессий

Один Workspace на проект (корень репозитория): все роли работают в нём, а код
задачи живёт в `worktrees/<id>` — каталог внутри проекта, поэтому песочница
`workspace-write` его разрешает. Карточка задачи лежит в основном чекауте
(`.kanban/tasks/<id>.md`), переходы делаются оттуда же — скрипт находит карточку
и коммитит её в `main`:

```bash
bin/task-move.sh 007 in-progress --owner "$DSH_SESSION_ID" --role worker
```

Код правится только в ветке задачи: `cd worktrees/007` (ветка `task/007`), там же
прогоняются тесты и делается коммит. Доска читает и карточки из основного
чекаута, и карточки открытых worktree, синхронизация не нужна.

Почему так: Workspace один, песочница разрешает запись в любой подкаталог
проекта, а карточка в `main` не даёт веткам задач расходиться по `.kanban/`.
Worktree создаётся **при выдаче** задачи (`git worktree add worktrees/<id> -b
task/<id> main`), чтобы ветка начиналась от актуального `main`.

## Жизненный цикл задачи

0. **Оркестратор** режет спеку: `bin/task-new.sh "Название" --backlog --spec 001
   --no-worktree` создаёт карточку в `backlog` в основном чекауте; `--owner` не
   ставится.
1. **Оркестратор** выдаёт карточку: заводит worktree от текущего `main`
   (`git worktree add worktrees/<id> -b task/<id> main`) и переводит карточку
   `todo` с владельцем и полями ветки/дерева; выдача идёт по порядку id и не
   больше трёх задач в конвейере.
2. **Исполнитель** берёт `todo` → `in-progress`, работает только в файлах
   задачи, коммитит в ветку, сдаёт `in-progress` → `in-review` с заметкой «что
   сделано, как проверить, результат тестов».
3. **Ревьювер** читает диф (код, а не только заметку): `in-review` → `testing`
   или возврат `in-progress` с замечаниями в карточке.
4. **Тестировщик** проверяет независимо: `testing` → `ready` или возврат
   `in-progress` с причиной и шагами воспроизведения.
5. **Оркестратор** вливает: `bin/task-commit.sh <id>` — `merge --no-ff` с
   сообщением `[<id>] <заголовок карточки>`, карточка → `merged`; затем
   `git worktree remove worktrees/<id>`.

## Правила

1. **Один worktree на задачу.** Свою рабочую директорию не меняем, за пределы
   проекта не пишем.
2. **Исполнитель не трогает чужие и общие файлы** (`package.json`, lock-файлы,
   схемы, миграции, `AGENTS.md`, `.kanban/`, `PLAN.md`). Нужны изменения —
   задача уходит в `blocked` с причиной, развязывает оркестратор. Исключение —
   задача, которая эти файлы и создаёт: граница пишется в карточке.
3. **Общие файлы меняет только оркестратор** — в основном чекауте и после того,
   как понял, какие задачи это затрагивает.
4. **Коммит только по путям задачи**: `git add <файлы>`, никогда `git add -A`.
5. **Один `in-progress` на агента.** Взял — сразу перевёл карточку.
6. **Задачу выдаёт оркестратор** и только закреплённую за сессией.
7. **Статус — только через карточку**, устные договорённости не видны доске.
8. **Слияние — только оркестратор и только через `bin/task-commit.sh`** из
   статуса `ready`. `task-move.sh <id> merged` запрещён.
9. **`git push` не делает ни один агент** — это шаг человека.
10. **Расход пишется в карточку**: `--role <роль> --tokens auto`.

## Лимиты и очередь

- Не больше **трёх** задач одновременно в `in-progress` + `in-review` +
  `testing`. Четвёртая ждёт в `todo`/`backlog`.
- `minTodo` = 0 (`.kanban/board.json`): сигнал «пополни todo» выключен. Пока
  один исполнитель и задачи фазы 0 зависят друг от друга, следующую карточку
  выдаёт оркестратор после слияния предыдущей. На параллельной фазе значение
  поднимается до 3.
- Пул исполнителей — `.kanban/.workers.json` (порядок = приоритет).
- Занятая роль — очередь, а не затор: карточка ждёт в `in-review`/`testing`, а
  исполнитель берёт следующую закреплённую за ним.
- Возврат `ready` → `in-progress` делает оркестратор при конфликте слияния.

## Доска

`dsh-kanban` смонтирован в профиле DSH Web, а этот проект перечислен в его
`boards` (`~/.dsh/cordis.patch.yml`). Карточки — `.kanban/tasks/<id>.md`,
формат — `.kanban/tasks/README.md`. Служебные файлы доски
(`.kanban/.watcher-*.json`, `.workers.json`, `worktrees/`) закрыты
`.gitignore`; `board.json`, `specs/` и `tasks/` — в git.

## Подсказки по командам

```bash
bin/task-new.sh "Название" --backlog --no-worktree --spec 001   # нарезка
git worktree add worktrees/007 -b task/007 main             # дерево при выдаче
bin/task-move.sh 007 todo --owner <session-id> \
  --branch task/007 --worktree "$PWD/worktrees/007"         # выдача
bin/task-move.sh 007 in-progress --owner "$DSH_SESSION_ID" --role worker
bin/task-move.sh 007 in-review --role worker --tokens auto --note "..."
bin/task-commit.sh 007                            # слияние (только оркестратор)
bin/backlog-fill.sh                               # добрать todo до minTodo
bin/board-sync.sh --print                         # какие карточки открыты
```
