# 001 — MVP dsh-memory: нарезка задач

Статус: принята 2026-11-09. Источник: внутренняя спецификация проекта (в
репозиторий не публикуется) и [`PLAN.md`](../../PLAN.md).

## Цель MVP

Плагин DSH, который даёт агенту долгосрочную память проекта и каскад
«L0 → L1 → L2 → L3» с записью проверенного ответа обратно в память.

Границы MVP: фазы 0–2 плана плюс измеримая приёмка (фаза 3). Фазы 4–5 —
исследовательские задачи, их результат — дизайн и прототип, а не готовая
функция.

## Правила нарезки

- Одна карточка — один проверяемый результат, который помещается в один worktree
  и одну ветку.
- Зависимости заданы порядком id: задача выдаётся, когда предыдущая влита в
  `main`, если карточка явно не говорит обратного.
- Лимит в работе — 3 задачи (`in-progress` + `in-review` + `testing`).
- Критерии готовности каждой карточки — проверяемые команды или артефакты, а не
  «сделано хорошо».

## Критерии готовности

### 001 Скелет плагина

- пакет `dsh-memory` с ESM-точкой входа, `dsh.bundle` и `cordis.patch.yml`, ряд
  монтирует плагин в профиль;
- модуль загружается `node --input-type=module` без ошибок и экспортирует
  `apply(ctx)`;
- юнит-тест на мок-`ctx` подтверждает регистрацию плагина и отсутствие падения
  без сервисов;
- `npm pack --dry-run` включает `lib/`, `cordis.patch.yml`, `package.json`.

### 002 Хранилище SQLite

- модуль открывает БД по пути из конфига, включает WAL, применяет миграции
  идемпотентно;
- схема: `sources`, `entries`, `entries_fts` (FTS5 с синхронизацией),
  `metrics`; поле `hash` уникально;
- namespace изолирует записи: поиск и запись не видят чужие namespace;
- тесты на временной БД: вставка, выборка, FTS5-поиск, повторное открытие.

### 003 Индексатор документов

- CLI `dsh-memory index --workspace <path>` обходит `**/*.md`, исключает
  `.git`, `node_modules`, `dist`, `build`, `tmp`, `.cache`, `worktrees`;
- фильтры секретов: `*.env`, `*secret*`, `*credential*`, строки `-----BEGIN`,
  `ghp_`, `sk-`, `AKIA`, `.git-credentials`;
- чанкование по заголовкам `##`, ≤ 800 токенов (оценка), `title` = «файл →
  раздел», ссылка на `source_path`;
- инкрементальность по `sha256` + `mtime`: неизменённые файлы не переиндексируются;
- тест на фикстурном каталоге: число чанков и пропуск секретов проверяемы.

### 004 `memory.search`

- FTS5 `MATCH` + `bm25`, `top-k` с параметром `k`;
- фильтры `kinds`, `status` (`verified` | `all`), `namespace`;
- `stale` не возвращается никогда, `draft` помечен в результате;
- сниппет ≤ 300 символов, сортировка по score;
- пустой/невалидный запрос даёт пустой массив, а не исключение.

### 005 `memory.write`

- вставка записи `draft` с `hash = sha256(kind|title|text)` и UNIQUE;
- дубликат по `hash` повышает `confidence`, объединяет `sources`, возвращает
  `deduped: true`;
- запись без источника допустима только как `draft` и `confidence < 0.5`;
- возвращает `{ id, deduped, status }`; `verified` напрямую не пишется.

### 006 `memory.verify`, `memory.invalidate`

- `verify` переводит `draft` → `verified`; без источника и без `verified_by`
  отказывает;
- `invalidate` по `path`/`ref` помечает связанные записи `stale` и возвращает
  число затронутых;
- TTL применяется при выборке: `decision` 180 дней, `fact` 60, `answer` 30;
- тест: после `invalidate` `search` не находит запись.

### 007 `memory.stats`, события

- `stats` возвращает `entries`, `by_status`, `hit_rate`,
  `tokens_saved_estimate`;
- события `search`, `write`, `verify` пишутся в `metrics` с полями
  `query_hash`, `hits`, `latency_ms`;
- `hit_rate` считается по событиям и не падает на пустой базе.

### 008 Конфигурация и env

- конфиг-схема плагина повторяет блок `dsh-memory` из README (namespace,
  db_path, inject, search, index, embeddings, verify) с дефолтами;
- `DSH_MEMORY_DB`, `DSH_MEMORY_INJECT`, `DSH_MEMORY_TOP_K` перекрывают конфиг;
- `namespace: auto` = имя каталога воркспейса;
- невалидный конфиг не роняет плагин: дефолты + предупреждение в лог.

### 009 Тесты и приёмка фазы 0

- фикстуры с тремя известными определениями из документации проекта;
- e2e-тест: `index` строит индекс, `search` находит все три определения;
- `npm test` зелёный, ключевые модули покрыты;
- README дополнен командой установки и примером запроса.

### 010 Инъекция top-k

- на каждом ходе поиск по первым 200 символам последнего сообщения;
- не более 3 записей и ≤ 600 токенов, формат `[memory] title — snippet (source, status)`;
- нет попаданий — блок не добавляется, 0 токенов;
- `DSH_MEMORY_INJECT=off` отключает инъекцию;
- ошибка поиска не ломает ход; добавка к первому токену измерена и ≤ 50 мс.

### 011 Метрики и `token-meter`

- события `route` (`layer`, `reason`, `tokens_saved_estimate`) пишутся в `metrics`;
- при доступном `dsh-token-meter` метрики публикуются, при отсутствии — no-op;
- `stats` показывает hit-rate и оценку экономии; тест на расчёт.

### 012 Мягкий каскад

- пресет `triage` с дешёвой моделью описан и подключается конфигом;
- правило «сначала `memory.search`, затем L2, затем L3» зафиксировано в
  `AGENTS.md`/README;
- после ответа L2/L3 выполняется `memory.write` (`draft`) с источником;
- тест: при попадании в память L3 не вызывается (мок-провайдер).

### 013 Верификация

- `verified` ставится только с источником и `verified_by`; правило проверяется
  тестом;
- запись от модели имеет `confidence ≤ 0.6` и статус `draft`;
- PASS ревью/теста или подтверждение человека — единственный путь в `verified`;
- README/AGENTS описывают правило «в память пишем только проверенное».

### 014 Индексация решений и доски

- индексируются `.kanban/tasks/*.md`, `docs/adr/*`, README компонентов;
- переиндексация удалённого/изменённого файла переводит записи в `stale`;
- TTL-политика применяется к `decision`/`fact`/`answer`;
- тест: удалили файл → запись не выдаётся.

### 015 Бенчмарк MVP

- сценарий из 20 повторяющихся вопросов по проекту;
- замер токенов до/после и hit-rate; отчёт в `docs/`;
- цели: hit-rate ≥ 20%, −25% токенов на повторных вопросах;
- бенчмарк запускается одной командой и воспроизводим.

### 016 Эмбеддинги (опция)

- конфиг `embeddings.enabled` и модель; таблица `embeddings`;
- гибридный поиск, при выключенных эмбеддингах — чистый FTS5;
- сравнение качества и латентности с FTS5 в отчёте;
- дефолт — выключено.

### 017 Жёсткий роутер L2→L3

- дизайн-док: точка входа хода, стриминг, отмена, таймауты, логирование;
- прототип: маршрутизация на L2 при уверенности, иначе L3; решение пишется в
  `metrics`;
- фича-флаг выключен по умолчанию;
- тесты на выбор слоя и на отсутствие регрессии при выключенном флаге.

### 018 Реестр ролей и диспетчер

- дизайн-док: реестр ролей (имя, промпт, модель, namespace), протокол
  диспетчера, агрегация и разрешение конфликтов, критерии приёмки фазы 5;
- прототип маршрутизации подтем на моках;
- риски и открытые вопросы зафиксированы; `PLAN.md` обновлён.
