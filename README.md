# dsh-memory

Долгосрочная память проекта и каскадное расходование токенов для агентов DeepSeek Harness (DSH).

**English version:** [README.en.md](README.en.md)

> **Статус: фаза 0 закрыта.** Работают скелет плагина, хранилище SQLite, индексатор
> с CLI `index` и модули `memory.*` (`search`/`write`/`verify`/`invalidate`/`stats`)
> с TTL и метриками; e2e «`index` → `search` находит три определения» зелёный.
> Инъекция top-k, каскад L2/L3 и бенчмарк — дальше по доске ([PLAN.md](PLAN.md)).

## Проблема

Каждая агентская сессия начинается с нуля: агент заново читает документацию и код и повторно
отвечает на те же вопросы, а знания не переживают сессию. Токены уходят на повторное чтение.

## Что делает

Проект задуман как память и каскад, которые:

- сохраняют знания между сессиями, чтобы не читать и не выводить одно и то же заново;
- ищут ответ по каскаду: бесплатные источники → RAG-память → дешёвая сабмодель → основная модель;
- пишут в память только проверенное: у записи есть провенанс и статус, галлюцинация не станет истиной;
- показывают эффект в цифрах: hit-rate памяти, оценка сэкономленных токенов, добавка к задержке.

## Установка и первый запуск

```bash
dsh plugin --profile web add <путь к пакету>   # затем перезапустить DSH Web
```

- настраивать ничего не нужно: память локальная (SQLite FTS5), сеть не используется, ключи не требуются;
- `dsh-memory index` — индексация markdown-документации вручную (инкрементально, с отсечением секретов);
- планируется позже (вне фазы 0): `dsh-memory doctor` (путь БД, namespace, файлы/чанки,
  отсеянные секреты), `dsh-memory index --dry-run` и фоновая автоиндексация при первом
  ходе с отключением через `DSH_MEMORY_AUTOINDEX=off`;
- векторы в основной пакет не входят: при необходимости ставится отдельный `dsh-memory-embeddings` (позже),
  и только он работает с провайдером или локальной моделью; дизайн, границы доверия и критерии 016 —
  [docs/embeddings-design.md](docs/embeddings-design.md).

### Первый запрос

```bash
# 1. Индексация markdown-документации воркспейса (CLI из пакета).
#    --json печатает отчёт: files / indexed / chunks / revived / stale / removed / skipped / secrets.
#    --namespace задаёт имя памяти; без него берётся имя каталога воркспейса.
dsh-memory index --workspace . --namespace dsh-memory --json

# 2. Поиск по памяти. В профиле DSH это делает инструмент memory.search;
#    в checkout пакета тот же вызов проверяется напрямую:
node --input-type=module -e "
  import { openStore } from './lib/store.js'
  import { searchMemory } from './lib/search.js'
  const store = openStore({ dbPath: '~/.dsh/memory', namespace: 'dsh-memory' })
  console.log(searchMemory(store, { query: 'каскад L0 L1 L2 L3', k: 3 }))
"
```

Запрос `memory.search` выглядит так: `{ "query": "каскад L0 L1 L2 L3", "k": 3 }`;
ответ — массив сниппетов `[{ id, title, snippet, source_path, source_ref, status,
confidence, score }]`, полный текст документа в выдачу не попадает.

## Как это работает

```text
запрос агента
  │
  ▼
[L0] детерминированные источники: доска, карточки, grep/glob  — 0 токенов
  │ промах
  ▼
[L1] RAG-память: SQLite FTS5, top-k сниппетов                 — 0 токенов
  │ промах
  ▼
[L2] дешёвая сабмодель: ANSWER | NO_ANSWER, max_tokens        — мало токенов
  │ NO_ANSWER
  ▼
[L3] основная модель из настроек сессии                       — дорого
  │
  ▼
ответ → write-back: дистилляция → draft → проверка → verified
```

- **L0 — детерминированные источники.** Доска задач, карточки, `grep`/`glob` по файлам: 0 токенов.
- **L1 — RAG-память.** Top-k сниппетов из локального индекса SQLite FTS5. Тоже 0 токенов модели.
- **L2 — дешёвая сабмодель.** Отвечает по контракту `ANSWER | NO_ANSWER`, только если уверена.
- **L3 — основная модель.** Модель из настроек сессии, вызывается только после `NO_ANSWER` на L2.
- **write-back.** Успешный ответ дистиллируется в запись, получает провенанс и статус `draft`;
  после PASS ревью/теста или подтверждения человеком запись становится `verified` и живёт на L1.

**Правило каскада.** Перед ответом моделью — `memory.search` (L1). Промах — пресет `triage`
(L2: дешёвая модель `deepseek-v4-flash`, контракт `ANSWER | NO_ANSWER`; маркеры распознаются
с хвостовой пунктуацией — `NO_ANSWER.` это отказ, а не ответ). `NO_ANSWER` — основная
модель (L3). Ответ L2/L3 дистиллируется в память как `draft` с источником (write-back), `verified`
ставится только подтверждением (006/013).

Ключевое правило — **в память пишется только проверенное**. Иначе галлюцинация сохранится в RAG
и будет тиражироваться дешевле, чем проверялась, а заметить её станет труднее.

Запись от модели (write-back каскада) создаётся только как `draft` и `confidence ≤ 0.6`;
write-back обязан передавать `author` вида `cascade:*`/`model*`/`triage*`, иначе запись
неотличима от человеческой. `verified` ставится исключительно `memory.verify`: нужен
источник и подтвердитель — PASS ревью/теста (`reviewer:…`/`verifier:…`/`tester:…`) или
человек (`human`); голый id сессии не принимается, чтобы сессия не могла подтвердить саму
себя. `memory.write` не умеет писать `verified` напрямую. Ручное исключение: только
`human` может подтвердить запись без источника при `requireSource: false` — это явный
человеческий акт, а не PASS ревью/теста.

## Память (RAG)

Поиск лексический, без векторов и сети: FTS5 по стеммированному индексу
(русский Snowball + мягкие основы), trigram-индекс для опечаток и подстрок,
синонимы из `data/synonyms.json` (выключаются `search.synonyms: false`) и
отдельный канал `verified` Q&A: ответы с совпадением в заголовке идут выше
обычных сниппетов (только в лексическом движке и статусе `verified`). Чистый `unicode61` остаётся как движок сравнения
(`engine: "unicode61"` / `dsh-memory bench --compare`).

| Свойство | Как планируется |
|---|---|
| Хранилище | SQLite, файл `~/.dsh/memory/<namespace>.db`: `entries` (`kind` = `doc`, `decision`, `fact`, `answer`, `code-note`), `entries_fts` (FTS5), `sources`, `metrics` |
| Namespace | воркспейс (рабочее пространство): память разных проектов не смешивается |
| Статусы | `draft` — черновик, `verified` — проверено, `stale` — устарело |
| Провенанс | `source_path` и `source_ref`, автор, время создания и обновления |
| Дедупликация | `hash = sha256(kind\|title\|text)` уникален: при совпадении растёт confidence и обновляются источники |
| Индексация | `.kanban/tasks/*.md` и `docs/adr/*` → `decision` (TTL 180 дней), README компонентов и прочая документация → `doc`; фронтматтер карточек не мешает, чанки режутся по `##` |
| Инвалидация | изменился sha256 файла или файл удалён → чанки индексатора становятся `stale` (текст остаётся в БД для аудита, но не выдаётся поиском); `stale` не выдаётся никогда. Удаление источников действует в пределах namespace: штатно `namespace: auto` — один namespace на воркспейс |
| TTL | `decision` — 180 дней, `fact` — 60, `answer` — 30 |

## Инструменты

| Инструмент | Назначение | Вход → выход |
|---|---|---|
| `memory.search` | поиск по памяти | `{ query, k?, kinds?, status?, namespace? }` → `[{ id, title, snippet, source_path, source_ref, status, confidence, score }]`, сниппет ≤ 300 символов |
| `memory.write` | записать знание | `{ text, title, kind, sources[], confidence?, status? }` → `{ id, deduped, status }` |
| `memory.invalidate` | пометить устаревшее | `{ path?, ref? }` → `{ affected }` |
| `memory.verify` | подтвердить запись | `{ id, verified_by }` → `{ id, status: "verified" }` |
| `memory.stats` | метрики памяти | `{}` → `{ entries, by_status, hit_rate, injected_tokens, tokens_saved_estimate }` |

`memory.search` по умолчанию отдаёт только `verified`; `status: "all"` добавляет `draft`
с пометкой статуса.
`memory.write` без источника — только `draft` с confidence < 0.5; при совпадении хэша растёт confidence.

## Инъекция контекста

- запрос берётся из первых 200 символов последнего сообщения пользователя;
- не более 3 записей на ход, суммарный бюджет ≤ 600 токенов;
- формат блока: `[memory] title — snippet (source, status)`;
- ничего не найдено — блок не добавляется, 0 токенов;
- отключается флагом окружения `DSH_MEMORY_INJECT=off`;
- добавка к задержке ≤ 50 мс, ход не блокируется.

## Диспетчер и специализированные сабмодели (предложение)

Диспетчер с реестром специалистов может заменить одну дешёвую сабмодель на L2: запрос он получает после
промаха L0/L1, делит на подтемы и раздаёт специалистам.

```text
запрос агента после промаха L0/L1
       │
       ▼
 ┌───────────┐
 │ диспетчер │  тематика → подтемы → маршрутизация по ролям
 └─────┬─────┘
       ├──▶ developer   разработка ПО
       ├──▶ designer    дизайн
       ├──▶ reviewer    ревью кода developer
       ├──▶ tester      тестирование всех видов
       └──▶ scientist   физика, математика, химия
       │
       ▼
 агрегация: сбор ответов, разрешение конфликтов
       ├── ответ есть ───▶ ответ агенту, write-back в общую память
       └── ответа нет ───▶ эскалация на L3
```

| Роль | Зона ответственности |
|---|---|
| developer | разработка ПО: реализация, отладка, рефакторинг; правки по замечаниям ревьювера |
| designer | дизайн: интерфейсы, UX, визуальные и интерактивные решения |
| reviewer | строгое непредвзятое ревью кода developer; замечания возвращает автору, сам код не правит |
| tester | тестирование всех видов: модульное, интеграционное, сценарное (end-to-end), граничные случаи |
| scientist | физика, математика, химия, биология и смежные дисциплины |

Специалист отвечает из своих знаний и RAG-памяти, при отсутствии ответа эскалирует на L3.
Диспетчер собирает ответы, разрешает конфликты и решает, нужна ли эскалация; цикл developer → reviewer →
исправления идёт до PASS, write-back попадает в общую verified-память. Ни один специалист не подписывает
собственную работу: ревью делает reviewer, тесты — tester, независимо от developer.

Роли расширяются через реестр: роль — это промпт, модель и зона ответственности; новая специализация
добавляется без переделки диспетчера. Статус: **предложение**, фаза после MVP. Риски: задержка, стоимость
координации, ошибки маршрутизации, конфликтующие ответы, версионирование промптов и ролей.

## Конфигурация

Блок `dsh-memory` в `~/.dsh/cordis.patch.yml`; дефолты и разбор окружения живут в
`lib/config.js`, конфиг ряда и `DSH_MEMORY_*` перекрывают их.

```yaml
dsh-memory:
  namespace: auto                                  # auto = имя воркспейса
  db_path: ~/.dsh/memory
  inject: { enabled: true, top_k: 3, token_budget: 600 }
  search: { default_status: verified, snippet_chars: 300, synonyms: true }
  index:
    include: ["**/*.md"]
    exclude: [".git/**", "node_modules/**", "target/**", "dist/**", "tmp/**", ".cache/**"]
    max_chunk_tokens: 800
  embeddings: { enabled: false, model: "" }   # legacy-поле; провайдеры — в dsh-memory-embeddings
  verify: { require_source_for_verified: true }
  cascade:
    enabled: false                                 # мягкий каскад L1 → L2 (triage) → L3
    preset: triage                                 # presets/triage.json: дешёвая модель, ANSWER | NO_ANSWER
    model: ""                                      # перекрывает модель пресета (deepseek-v4-flash)
    max_tokens: 300
    write_back: true                               # ответ L2/L3 → memory.write (draft с источником)
```

Переменные окружения: `DSH_MEMORY_DB`, `DSH_MEMORY_INJECT`, `DSH_MEMORY_TOP_K`.

Пресет `triage` — это дескриптор каскада (`presets/triage.json`: дешёвая модель,
контракт `ANSWER | NO_ANSWER`, `max_tokens`), а не DSH agent preset: маршрутизацией
управляет `lib/cascade.js`, включение — секцией `cascade` выше. После ответа L2/L3
каскад пишет дистиллят в память как `draft` с источником (`write_back`). Если провайдер
не вернул источники, запись получает синтетический `source_ref` `cascade:L2`/`cascade:L3`.
`cascade.enabled: false` — это штатная семантика «без дешёвой модели»: память (L1)
ищется всегда, затем сразу основная модель (L3).

## Бенчмарк

Бенчмарк MVP запускается одной командой и воспроизводим: фикстуры
(`bench/fixtures/project`) и 20 вопросов (`bench/questions/questions.json`)
лежат в пакете, текущая дата и сеть не используются. Числа в отчёте получены
на этой фикстуре (10 документов), а не на реальном корпусе проекта: это
приёмочный тест механики, а не обещание −44% на любом проекте.

```bash
dsh-memory bench --report docs/benchmark-mvp.md
```

«До» — полный текст источника ответа, «после» — инъекция L1 (top-k сниппетов,
бюджет 600 токенов) плюс источник при промахе. Попадание считается релевантным
только при совпадении `source_path`, поэтому слабые совпадения `matchMode: any`
не засчитываются как экономия. Цели: hit-rate ≥ 20%, экономия ≥ 25% токенов;
отчёт с числами и таблицей вопросов — [docs/benchmark-mvp.md](docs/benchmark-mvp.md).
Код возврата 0 — цели достигнуты, 1 — нет.

### Реальный корпус

Отдельный сценарий — 20 вопросов по реальным документам репозитория (README,
AGENTS, PLAN, спеки, карточки); фикстуры `bench/` из индекса исключаются, чтобы
вопросы не отвечал сам бенчмарк:

```bash
dsh-memory bench --workspace . --questions bench/questions/real.json \
  --compare --with-fixture --report docs/benchmark-real.md
```

Отчёт [docs/benchmark-real.md](docs/benchmark-real.md) содержит точные числа,
промахи и сравнение с фикстурой 015 и чистым `unicode61`. На текущем корпусе
лексический поиск даёт hit-rate около 80% и экономию около 77% (у `unicode61` —
около 65% и 64%); промахи — широкие смысловые вопросы. Вывод: для точных терминов
лексики достаточно, векторы не обязательны для MVP и остаются опцией (021/016).
Временная БД используется всегда, если не задан `--db-path`; `DSH_MEMORY_DB`
на `bench` не влияет.

## Эмбеддинги (опция)

По умолчанию выключены: поиск — чистый FTS5. Опциональный пакет
[`packages/dsh-memory-embeddings`](packages/dsh-memory-embeddings/README.md)
даёт локальные (офлайн, без ключей) или OpenAI-совместимые/Ollama эмбеддинги,
хранит векторы в SQLite BLOB и добавляет гибридный RRF BM25 + косинус через
`memory.registerSearchChannel`. Основной пакет не получает сетевой код; весь
egress — в опциональном пакете, ключ только из env, `DSH_MEMORY_NO_NETWORK=1`
запрещает сеть. Сравнение качества и латентности с FTS5 —
[docs/benchmark-embeddings.md](docs/benchmark-embeddings.md); дизайн и
критерии — [docs/embeddings-design.md](docs/embeddings-design.md).

## Метрики

| Цель | Метрика | Планка MVP |
|---|---|---|
| Повторные вопросы дешевле | токены на повторяющихся вопросах | −25% |
| Память используется | hit-rate L1 | ≥ 20% |
| Записям можно доверять | доля `verified` с провенансом | 100% |
| Нет знаний без источника | записи `verified` без источника | 0 |
| Память не тормозит ход | добавка к первому токену | ≤ 50 мс |
| Инъекция остаётся компактной | размер блока инъекции | ≤ 600 токенов |

Семантика `memory.stats`: `injected_tokens` — расход на инъекции памяти (каждый
ход добавляет снапшот-блок в историю, поэтому расход копится); `tokens_saved_estimate`
— экономия только там, где ход обслужен L2 вместо L3, в MVP остаётся 0 до
калибровки бенчмарком 015. `dsh-token-meter` (если доступен) используется как
авторитетный оценщик токенов (`estimateMessage`); канала публикации метрик в
нём нет, метрики живут в собственной таблице `metrics`.

## Границы и безопасность

Чего проект делать не собирается:

- не заменяет `AGENTS.md` и `CLAUDE.md` — правила проекта остаются правилами проекта;
- в MVP нет глобальной памяти между проектами: namespace равен воркспейсу;
- нет обучения на переписке без верификации;
- векторный поиск не обязателен: в MVP его заменяет FTS5;
- своего интерфейса нет — всё живёт в инструментах и плагинах DSH.

Приватность: индекс локальный, по умолчанию сеть не используется вообще (векторы — только в опциональном пакете); исключаются файлы `*.env`,
`*secret*`, `*credential*`, `.git-credentials` и ключи, опознаваемые **по форме**:
PEM-заголовок в начале строки (`-----BEGIN … PRIVATE KEY-----`), `ghp_` + 36
символов, `sk-` + 48 символов, `AKIA` + 16 заглавных. Голые упоминания маркеров и
PEM-заголовок посреди описания (README, спека, карточки задач) секретом не
считаются — иначе документация проекта выпадала бы из памяти; ключ в inline-code,
списке или fenced-блоке по-прежнему отсекается. `memory.search` отдаёт только
сниппеты. При ошибке плагин молчит, ход продолжается без памяти.

## Дорожная карта

| Фаза | Содержание | Приёмка |
|---|---|---|
| 0 | скелет плагина, `memory.search`/`memory.write`, SQLite FTS5, CLI `index` | `index` строит индекс по документации, поиск находит три известных определения |
| 1 | инъекция top-k, `memory.stats`, дедупликация, `stale` по хэшу | hit-rate ≥ 20% на 20 запросах, инъекция ≤ 600 токенов |
| 2 | статусы `draft`/`verified`, пресеты triage, правила в `AGENTS.md` | ни одной `verified`-записи без источника, экономия измерена |
| 3 | индексация `.kanban` и решений, TTL, `memory.invalidate` | устаревшие записи не выдаются |
